# Implementation research — September 11, 2026

Research used upstream project documentation and source code, alongside measurements on this machine. Firecrawl was installed but required authentication, so its search could not run; the upstream pages were retrieved with the available web tool instead.

**Inference and GPU initialization.** Faster-whisper uses CTranslate2, supports quantized GPU/CPU execution, provides word timestamps, and integrates Silero voice detection. Its documentation specifies CUDA/cuBLAS and cuDNN requirements and stresses that transcription runs when the segment generator is consumed. The app therefore configures the installed runtime directories, consumes a warm-up decode, and falls back to CPU when GPU execution fails. See [faster-whisper](https://github.com/SYSTRAN/faster-whisper).

On the Quadro T2000, a six-second excerpt decoded with tiny.en at beam 1 had a median time of 0.267 seconds in float16 versus 0.214 seconds in int8_float16. Small.en at beam 3 measured 1.844 versus 1.069 seconds. Each median uses three iterations after a warm-up. The text was identical across precisions for this excerpt; that is not a broad equivalence test. The app chooses int8_float16 when supported.

**Live transcript stability.** Whisper-Streaming explains why appending independently decoded overlapping windows is unreliable and describes confirming stable prefixes across successive hypotheses. Its repository now points to SimulStreaming as its successor. The new app uses a simpler, original phrase-based design: an utterance has one replaceable draft, finalized at a detected pause. Continuous turns are bounded, retain audio context across the boundary, and use word timestamps to decide which side owns each boundary word. It does not claim to implement the complete LocalAgreement or AlignAtt algorithms. See [Whisper-Streaming](https://github.com/ufal/whisper_streaming) and [SimulStreaming](https://github.com/ufal/SimulStreaming).

The engineering choice is to keep the existing faster-whisper runtime and small local models on this 4 GB GPU while fixing capture, scheduling, and transcript state. A complete SimulStreaming migration would introduce a different inference stack and would need a separate quality, latency, and memory evaluation; it was not necessary to resolve the measured duplication defect.

**Windows audio.** SoundCard documents channel maps, native-channel capture, and platform-specific WASAPI limitations, including single-channel capture concerns. The new capture path uses explicit native-channel maps and an actual mean across channels, captures in 96 ms blocks with a larger recorder buffer, reports discontinuities, and selects devices by endpoint ID. Separate source tracks avoid confusing microphone data with playback data. See [SoundCard](https://github.com/bastibe/SoundCard). Acoustic echo cancellation remains outside the implementation; headphones avoid acoustic duplication in the two-source mode.

**UI threading.** Python's Tk documentation describes its event loop and threading behavior. All widgets, clipboard actions, dialogs, rendering, and control changes now run on the main Tk thread; workers send events through a queue. Audio capture, inference, device enumeration, and disk writes run separately. No worker calls a Tk method. See [Python Tkinter documentation](https://docs.python.org/3/library/tkinter.html).

**Observed improvement.** The old application failed inference until a runtime workaround was applied; with that workaround, a 64-word synthetic passage expanded to 166 words and first text arrived after 2.66 seconds. A rebuilt Balanced hardware run with tiny previews and small final decoding produced 61 whitespace-delimited words, with first text at 0.785 seconds, no repeated phrases, all entries finalized, and all capture threads stopped. The lower word count largely reflects numbers written as numerals. The previous model rendered a spoken time as money; the small model rendered it as `3.30` in that test. Results are sample-specific, and later runs may vary with hardware load. The final validation files record the currently configured precision and behavior.

The complete development verification includes deterministic state and failure-path tests, real model decoding, real Windows loopback playback, exports, and Tk button actions. It does not establish quality for a real multi-speaker call, acoustic echo, every supported language, or an hours-long soak test. No external service receives meeting audio.
